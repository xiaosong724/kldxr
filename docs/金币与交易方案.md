## 0. 结论先行

**一句话**：金币就是 `roles` 表上再加一列（跟魔气 `mq` 一模一样的做法 ✓）；
交易用**「tick 线程管状态机 + 存档线程单事务落库」**两段式 —— 因为 tick 线程不许碰磁盘 ✗
而"要么全成要么全不成"又必须在一个事务里 ✗ 这两条硬约束**只能**这么调和 ✓

```
① tick 线程         记会话状态、判距离/在线/超时/确认、上锁（内存）✓
                     └─ 一次落库 = 一条 post_save('TRADE', {...}) ✓
② 存档线程          在一个 SAVEPOINT 里做完全部 8 个动作 ✓
                     ├─ 成功 → RELEASE    → inbox 回一条 'tradres' ok ✓
                     └─ 失败 → ROLLBACK   → inbox 回一条 'tradres' 失败原因 ✓
③ tick 线程收到 ok  才改内存里的金币 ✓（★ 先落库、后改内存 —— 这样两边永不错开 ✓）
④ 网络线程          只做一件额外的活：把物品【同步锁上】（查库 + 判归属 + 判是否已装备）✓
                     （和现有的 equip / equiparmor 完全同构 ✓ 见 server/net.py:115 ✓）
```

**分 4 步落地**（每步都能单独验证 ✓ 详见 §5）：

| 步 | 内容 | 做完怎么验（可执行） |
|---|---|---|
| **1** | 数据层：迁移 v4（`roles.gold` + `items.locked_by` + `gold_log` + `trade_log`） | `python server\db.py` + 真库副本跑迁移 + 查 `PRAGMA table_info` |
| **2** | 金币本体：内存字段 + 掉落 + 流水 + 管理端发放/查账 | `python tools\test_gold.py`（离线，固定种子） |
| **3** | 交易：状态机 + 物品锁 + 单事务落库 + 协议 | `python tools\test_trade.py`（离线）+ 真库副本跑 `_save_trade` |
| **4** | 界面：交易窗 + 端到端 | 两个浏览器窗口手工跑一遍 + `python tools\check_core_dom.py` |

**5 个关键设计决定**（一句话一条 ✓ 后面每节都有展开）：

| # | 决定 | 为什么 |
|---|---|---|
| 1 | 金币加在 **`roles` 表**（不是单独表） | 一账号一角色（`roles.account_id UNIQUE` ✓ `db.py:43`），和魔气 `mq` 一个做法 ✓ 离线玩家天然就在库里 ✓ |
| 2 | 负数防线做 **三层**：`CHECK(gold>=0)` + `UPDATE...WHERE gold>=?` + 业务兜底 | ★ 实测过：光靠应用层判会漏 ✗ 光靠 CHECK 只会抛异常、给不出"钱不够"这种友好提示 ✗ |
| 3 | **所有金币变更都进 tick 线程**（管理端也走 `post_admin`） | ★ 这是第 155 轮踩过的坑：两处都写库 = "谁后写谁赢"✗ 最难查 ✓（`world.py:1601` 原话） |
| 4 | 交易的**唯一幂等键 = `sid`（会话号）**，落库靠 `trade_log.sid` 主键撞唯一约束 | ★ 不需要额外写"去重逻辑"✗ 数据库自己就是幂等闸门 ✓ |
| 5 | **TOCTOU 的判定一律下沉到 SQL 的 `WHERE` 里，用 `rowcount` 说话** | tick 线程的校验和落库之间有时间差 ✗ 只有"写的那一刻再判一次"才是真安全 ✓ |

## 1. 金币系统

### 1.1 定位与硬约束

```
金币 = 最基础的通货 ✓
用途（本轮先立住 4 条）：
  ① 打怪掉         ② 玩家之间交易        ③ 被 PvP 夺取（已有规则 ✓）
  ④ 管理员发放（测试/补偿 ✓）

硬约束（不能破）：
  ★ 一律【整数】—— 数据库列是 INTEGER，Python 侧一律 int()，★ 绝不用 float ✗
    （浮点会出现 0.1+0.2=0.30000000000000004 ✗ 对账永远对不平 ✓）
  ★ 永不为负 —— 见 §1.3
  ★ 只有 tick 线程改【在线玩家的内存值】，只有存档线程写库 ✓
```

### 1.2 ★ 决定 1：金币存在哪

**选择：`roles` 表加一列 `gold`。不建单独的 `wallets` 表。**

| 方案 | 好处 | 为什么不选 / 为什么选 |
|---|---|---|
| **A. `roles` 加一列** ✅ | 和现有 `mq`/`mq_at` 完全同构（`db.py:254` 就是这么加的 ✓）；`role_public()` 加一个字段就跟着 `welcome` 下发 ✓（`auth.py:135`）；离线玩家天然在库里 ✓ 不用额外查一次 | ★ **选它** |
| B. 单独 `wallets(role_id, gold)` 表 | 以后一个角色多币种（金银铜）好扩 | 现在只有一个币种 ✗ 多一张表 = 每次读金币多一次 JOIN ✓ 而且 `roles` 行本来就已经是热行（每 15 秒被 `_save_player` 更新一次 ✓ `world.py:3169`）→ 分表省不下任何东西 ✗ |
| C. 金币也是一种 `items` 行 | 一套代码搞定 | ✗✗ 灾难：金币要按数量合并、要能负向扣、要防重复堆叠 ✗ 而且 `items` 每行要存一大坨 `item_json` ✓ 完全不成比例 |

**和现有 `items` / `roles` 的衔接**：

```
roles  1 ──── n  items          （现有：items.role_id ✓ db.py:73）
roles  1 ──── n  gold_log       （新增：金币流水 ✓ 只增不改 ✓）
roles  1 ──── n  trade_log      （新增：a_role / b_role 两个外键 ✓ 但【不建 FK】见下）
items  1 ──── 0..1 trade 会话   （新增：items.locked_by 存会话号 ✓ 没锁 = NULL ✓）
```

> ★ 为什么不建 `FOREIGN KEY`：
> `db.py:209` 开了 `PRAGMA foreign_keys=ON` ✓ 一旦建了 FK，删角色（管理页的 `delplayer` ✓ `app.py:556`）
> 就会被流水表挡住 ✗ 变成"删不掉人"✗
> → **流水表故意不建 FK** ✓ 它是**审计账本**：人删了账还得留着 ✓ 这正是流水表的意义 ✓

### 1.3 ★ 决定 2：负数防护（三层，缺一不可）

```
第 ① 层  数据库 CHECK 约束        gold INTEGER NOT NULL DEFAULT 0 CHECK (gold >= 0)
          → 哪怕以后有人写错代码、直接 UPDATE 一个负数，SQLite 也会当场报
            IntegrityError: CHECK constraint failed: gold >= 0  ✓（★ 实测过 ✓ 见 §9）
          → 这是【最后一道闸门】：宁可报错，也绝不出现负余额 ✓

第 ② 层  扣款 SQL 一律带条件 + 看 rowcount
          UPDATE roles SET gold = gold - ? WHERE id = ? AND gold >= ?
          → rowcount = 1 = 扣成功 ✓  rowcount = 0 = 钱不够，什么都没发生 ✓
          ★ 关键：这是【原子】的 ✗ 不存在"先查余额、再扣"中间被人插一脚 ✗
          ★ 而且这一条天然给出"钱不够"这个可判断的结果 ✓ 比 CHECK 抛异常友好 ✓

第 ③ 层  业务层永远"不够就不扣、不扣就明确告诉玩家"
          例：夺取时 loser 只有 30 金币、规则要扣 100
              → 扣 30 还是什么都不扣？★ 见 §8 问题 ③（默认：什么都不扣 ✓ 和用户原话一致）
```

> ★ 为什么三层都要，不是多此一举：
> - 只有 ①：每次都要 catch IntegrityError 再翻译成人话 ✗ 而且 `post_save` 是异步的 ✓
>   异常发生在**存档线程**里 ✗ 玩家那边根本收不到"钱不够"✓（只会静默失败 ✓ 最难查）
> - 只有 ②：万一以后有人图省事写了 `UPDATE roles SET gold = ?`（绝对值）✗ 就没保护了 ✓
> - 只有 ③：应用层的判断在并发下会被绕过 ✗

### 1.5 流水表：要不要记账、记多少

**要记 ✓** 理由（用户点名的"可审计"）：

```
① 玩家吵起来"我的钱不见了" → 查 gold_log 一眼看到每一笔 ✓
② 防作弊：谁的钱在一分钟内涨了 10 万 → 一眼看出来 ✓
③ 对账：所有人余额之和 + 系统回收 = 总产出（能证明经济没漏水 ✓）
④ 交易纠纷：trade_log + 两边 gold_log 三条一起看 ✓
```

★ **但不能无脑全记** —— 算笔账 ✓：

```
一次击杀掉 5~20 金币 ✓ 10 个玩家挂机，每人每分钟杀 10 只
   → 100 条/分钟 → 144000 条/天 → 每行约 60 字节 → ★ 8.6 MB/天 → 一个月 260 MB ✗
   （game.db 现在才 1 MB ✓ 一个月涨 260 倍 ✗ 备份都会变慢 ✓）
```

**建议做法（推荐 B，但保留 A 供选）**：

| 方案 | 说明 | 代价 |
|---|---|---|
| A. 全记 | 每笔一行 | 库涨得快 ✓ 但最省心 ✓ |
| **B. 合并记** ✅ | **同一角色 + 同一 reason 的连续小额**，在 30 秒窗口内**合并成一条**（`delta` 累加 ✓ `balance` 取窗口末值 ✓） | 落盘量降到约 **1/50**（≈ 3~5 MB/月 ✓）；代价：看不到"第 37 只怪掉了 8 金币"这种粒度 ✗ 但**总账一分不差** ✓ |
| C. 全记 + 定期归档到 `gold_log_old` | 兼顾 | 要多写一个归档器 ✗ 本轮不值得 ✓ |

```
★ B 怎么实现（不复杂）：tick 线程里挂一个 acc
    world.gold_acc = {role_id: {'reason':…, 'delta':0, 'last':ts, 'ref':…}}
    · 每次加钱：并入 acc ✓
    · 满 30 秒 / 角色下线（_save_player 那一处 world.py:3169）/ reason 变了
      → 把这一条 post_save 出去 + 清 acc ✓
  ★ 而【跨玩家】的（trade / pvp_steal / admin）**一律不合并、逐笔立即落** ✓
     因为这几类才是真正要审计的 ✓ 量也小（一天几十条 ✓）
```

### 1.7 ★ 决定 3：内存里的金币 + 线程纪律

```
Player.__slots__ 加 'gold'        （world.py:109 —— ★ 一定要加进去 ✗
                                    world.py:121 的注释写着踩过两次这个坑 ✓）

  ① 只有 tick 线程改 p.gold ✓（HTTP 线程只能 post_admin ✓）
  ② 落库一律用【相对增量】`UPDATE roles SET gold = gold + ? WHERE id = ?`

     为什么：绝对值和 saver 的批量刷新会打架 ✗
       （`_save_player` 每 15 秒就把 roles 整行刷一次 ✓ world.py:3169 ✓

  ③ ★ 好消息：`self.saves` 是【单队列】+ 只有【一个】存档线程按 FIFO 取 ✓
     （world.py:211 / world.py:3177 ✓）
     → 我们投的金币增量是按顺序落盘的 ✓ 库里的余额和内存永远同步 ✓ 不用加锁 ✓
```

★ **为什么管理端也走 tick 线程**（这一条值得单独说）：

```
踩过的坑（第 155 轮，world.py:1601 原话）：
  "★ 千万别再写库 ✗ 两处都写就会出现'谁后写谁赢'✗ 最难查 ✓"
  （当时是魔气：管理页写了库 ✓ 但在线玩家内存里还是旧值 ✗
    而每 15 秒的定时存盘又把旧的刷回库 ✓ → 管理页设的值"过一会儿就没了"✓）

本方案的统一做法（比魔气那次更干净 ✓）：
  ★ 所有金币变更 → post_admin('gold', {...}) → tick 线程

```

## 2. 玩家交易系统

### 2.1 规则总表

| 规则 | 值 | 怎么判 | 备注 |
|---|---|---|---|
| 距离 | **≤ 5 米** | tick 线程算 `(a.x-b.x)²+(a.z-b.z)² > 25` 就拒 ✓ | ★ 用【权威坐标】✗ 不用客户端报的 ✓（和 `_party_op` 的邀请距离一个路子 ✓ `world.py:1980`） |

| 并发 | 一人同时只能有 **1 笔** | `world.trade_of[role_id]` 唯一 ✓ | |
| 人数 | **1 对 1** ✓ | 不做多方 ✓ | 多方容易变成变相拍卖行 ✗ |
| 超时 | **60 秒无操作** 自动取消 | tick 线程扫 `now - last > 60` ✓ | ★ 任何一方掉线 → **立刻**取消（不等 60 秒 ✓ 见 §4.1） |
| 确认 | 双方各点一次 ✓ | `a.ok && b.ok` | ★ 任一方改内容 → **双方确认一起清零** ✓（用户明确要求 ✓） |

| 背包容量 | 不限制 | 项目里背包本来就没容量上限 ✓（`bag_of` 的 `cap=2000` 只是传输上限 ✓ `auth.py:255`） | 物品一律进**背包**（`in_storage=0`）✗ 不进仓库 ✓ |
| 已装备的物品 | **不能交易** ✗ | 一条 SQL 就能判（见 §2.2 的 `lock_items` ✓） | ★ 要交易先脱下来 ✓ |
| 损坏的装备 | 可以交易 ✓ | 物品 JSON 里 `broken` 原样带过去 ✓ | 和现有行为一致 ✓（`auth.py:456`） |
| 等级门槛 | **没有** ✓ | 和现有穿戴规则一致 ✓（`auth.py:458` 的注释：能装、能看、能打，只是发挥不出来 ✓） | |

### 2.2 ★ 数据表设计（完整 SQL）

> ★ 下面的 SQL **全部在真库副本上跑过** ✓ 见 §9（副本来自 `server/game.db`：
> 114 个角色 · 1562 件物品 · `user_version=3` → 迁到 4 ✓）
> **当前版本号是 `SCHEMA_VERSION = 3`** ✓ 见 `server/db.py:16`

**迁移 v4**（追加在 `MIGRATIONS[3]` 之后 ✓ —— `db.py:254` 那个位置，★ 别插到 `MIGRATIONS` 定义之前 ✗ 那个坑 `db.py:253` 的注释里写着 ✓）：

```sql
-- ============ ① 金币：roles 加一列（照 mq 的做法 ✓）============
ALTER TABLE roles ADD COLUMN gold INTEGER NOT NULL DEFAULT 0 CHECK (gold >= 0)
-- ★ 为什么必须用 ALTER 而不是改建表语句：
--   CREATE TABLE IF NOT EXISTS 对【已存在的表】什么都不做 ✗
--   → 老库永远不会有 gold 列 → 一读就报 no such column ✗

ALTER TABLE items ADD COLUMN locked_by TEXT          -- NULL = 没锁；否则 = 占用它的交易会话号
-- ★ 为什么存 TEXT 而不是 INTEGER：
--   以后 sid 换成 uuid 也不用改列 ✓ 而且能一眼看出是哪个会话 ✓
-- ★ 为什么加在 items 上、而不是另建 item_locks 表：

-- ============ ③ 金币流水（审计账本 ✓）============

    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    role_id     INTEGER NOT NULL,                 -- 谁的钱动了（★ 故意不建 FK ✓ 见 §1.2 的说明）

);

CREATE TABLE IF NOT EXISTS trade_log (
    sid         TEXT    PRIMARY KEY,              -- ★★ 幂等键 ★★（重复提交 = 撞主键 = 整笔回滚 ✓）
    a_role      INTEGER NOT NULL,
    b_role      INTEGER NOT NULL,
    a_name      TEXT    NOT NULL,                 -- 名字快照（★ 人可能被删 ✗ 账要留 ✓）
    b_name      TEXT    NOT NULL,
    a_items     TEXT    NOT NULL DEFAULT '[]',     -- JSON：A 拿出来的物品 id 列表 [12,48]
    b_items     TEXT    NOT NULL DEFAULT '[]',     -- JSON：B 拿出来的

    a_x REAL NOT NULL DEFAULT 0,  a_z REAL NOT NULL DEFAULT 0,   -- 成交时双方位置（审计/反作弊）
    b_x REAL NOT NULL DEFAULT 0,  b_z REAL NOT NULL DEFAULT 0,
    result      TEXT    NOT NULL DEFAULT 'ok',     -- ok | rollback（失败也留一条 ✓ 才知道有人想干嘛）
    ts          INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_trade_a ON trade_log(a_role, ts);
CREATE INDEX IF NOT EXISTS idx_trade_b ON trade_log(b_role, ts);

-- ============ ⑤ 锁的索引（部分索引：只索引"被锁住的那几行" ✓）============
CREATE INDEX IF NOT EXISTS idx_items_lock ON items(locked_by) WHERE locked_by IS NOT NULL;
-- ★ 为什么是部分索引：99.99% 的行 locked_by 都是 NULL ✗
--   全量索引白占空间 ✓ 部分索引只装正在交易的那几件 ✓
```

**字段为什么要这么设计（逐条）**：

| 设计 | 为什么 |
|---|---|
| `gold_log.balance` 存**变动后余额**，不只存 delta | 对账时不用写"累加所有历史 delta"这种查询 ✓ 直接看最后一条就知道余额对不对 ✓ 而且能**自查**：`balance - delta` 应该等于上一条的 `balance` ✓ |
| `trade_log` 存**物品 id 列表**而不是整个 JSON | 物品的完整 JSON 在 `items` 表里 ✓ 不重复存（省空间 + 不会两份不一致 ✓）；★ 但**名字快照**要存 ✓ 因为角色可能被删（`app.py:556 delplayer`）✓ 账不能跟着消失 ✓ |
| `sid` 用 TEXT 主键 | 主键本身就是幂等闸门 ✓（§2.7 第 3 条）；TEXT 能带启动时间戳、重启不重复 ✓（§2.3） |
| `trade_log` 失败也写一条（`result='rollback'`） | ★ 有人反复尝试不可能的成交（比如拿别人的物品 id）→ 流水里全是 rollback → 一眼看出是攻击 ✓ |
| 位置也记 | 5 米限制的**事后复核**：两条流水位置差 300 米 → 说明当时的距离校验被绕过了 ✓ 排障神器 ✓ |

### 2.4 ★ 决定 4：状态机

```
状态一览（6 个）：
  invite    已发起，等对方点【同意】（对方还没接受）
  open      双方都进来了，正在放东西
  settling  双方都确认了，正在落库（★ 这个状态下【任何改动一律拒绝】✗）
  done      成交 ✓ 会话即将销毁
  failed    落库失败（余额不够 / 物品被抢走 / 重复 sid）✗ 会带着原因回到 open 吗？→ 不回 ✓ 直接销毁
  cancel    任一方取消 / 超时 / 掉线 / 距离超了 / 有人死亡 ✓ 会话销毁
```

**状态转移表**（★ 每一行都是一个要写测试的分支 ✓ 见 §6）：

| 从 | 触发 | 条件（全在服务器判 ✓） | 到 | 副作用 |
|---|---|---|---|---|
| — | A 发 `invite`（对方 role_id） | 双方都真在线 ✓ 非幽灵 ✓ 距离 ≤ 5 ✓ 都没在别的会话里 ✓ A 没被限流 ✓ | `invite` | 建会话 ✓ 推 `tradest` 给双方 ✓ 弹窗给 B ✓ |
| `invite` | B 发 `accept` | 会话还在 ✓ 没超时 ✓ 距离仍 ≤ 5 ✓ | `open` | 推双方：交易窗打开 ✓ |
| `invite` | B 发 `decline` | — | `cancel` | 告诉 A"对方拒绝了" ✓ |
| `invite` | 超时 60 秒 / 任一方掉线 | — | `cancel` | 告诉另一方"交易邀请过期了" ✓ |
| `open` | A 放/取物品 或 改金币 | 物品是他自己的 ✓ 在背包 ✓ 未装备 ✓ 未被别的会话锁 ✓；金币 ∈ [0, 他的余额] ✓ | `open` | **`a_ok = b_ok = False`** ✓ `rev += 1` ✓ 推双方 ✓ |
| `open` | B 放/取物品 或 改金币 | 同上（B 的视角） | `open` | **`a_ok = b_ok = False`** ✓ `rev += 1` ✓ 推双方 ✓ |
| `open` | 任一方 `confirm` | `rev` 与服务器一致 ✓ | `open` | 那一方 `ok = True` ✓ |
| `open` | 双方 `ok` 都 True | 再复检一次：双方在线 ✓ 距离 ≤ 5 ✓ 金币仍够 ✓ 物品锁还是这个 sid ✓ 不是 `settling` ✓ | `settling` | 推"正在结算…" ✓ `post_save('TRADE', …)` ✓ |
| `settling` | 存档线程回 `tradres: ok` | — | `done` | ★ **这时才改内存金币** ✓ 推结果 ✓ 双方客户端重拉 `/api/bag`（`app.py:667`）✓ 写两条 `gold_log` ✓（已在事务里做了 ✓） |
| `settling` | 存档线程回 `tradres: 失败` | — | `failed` | 解锁物品 ✓ 双方确认清零 ✓ 推失败原因 ✓ 会话销毁 ✓ |
| `open` / `settling` | 任一方 `cancel` | — | `cancel` | 解锁物品 ✓ 推双方 ✓ |
| `open` | 超时 60 秒无操作 | — | `cancel` | 同上 ✓ |
| `open` / `invite` | 任一方**掉线**（含幽灵） | — | `cancel` | ★ 立刻取消 ✗ **不等 60 秒** ✓（见 §4.1） |
| `open` | 距离 > 5 米（移动导致） | tick 里每 0.5 秒复检一次 | `cancel` | 推"你们走远了，交易取消" ✓ |
| `open` / `settling` | 任一方**死亡**（`hp <= 0`） | — | `cancel` | 推"你倒下了，交易取消" ✓ |
| `settling` | ★ 任何"改内容"请求 | — | 不变 ✓ | 回一句"正在结算，稍等" ✓（**拒绝** ✓ 这是防"结算中再改一笔"✓） |
| `settling` | ★ 任何 `confirm` 重复到达 | — | 不变 ✓ | 忽略 ✓（幂等 ✓） |
| `done`/`cancel`/`failed` | 任何请求 | 会话已从 `world.trades` 里删掉了 ✓ | — | 回"这笔交易已经结束了" ✓ |

> ★ "任何一方改动内容都要取消双方的确认状态"—— 就是表里那两行 `a_ok = b_ok = False` ✓
> **注意是把两个人的都清掉** ✗ 不是只清改的那个人 ✓（用户明确要求 ✓）
> 理由很实在：A 看到的是旧内容才点的确认 ✗ 内容一变他的确认就该作废 ✓

### 2.6 ★ 决定 5：落库 —— 单事务

```
走的通道：post_save('TRADE', (payload_json, ts))     （world.py:372 ✓ 任何线程都能投 ✓）

存档线程（world.py:3177 _run_saver）里加一支：
  if sql == 'TRADE':
      self._save_trade(db, params)      # ★ 和现有的 'PICK' 完全同构 ✓（world.py:3197 ✓）
      continue
```

**`_save_trade` 里的全部动作（一个 SAVEPOINT 包住 ✓ 实测过 ✓）**：

```
SAVEPOINT trade
  ① 扣 A 的金币  UPDATE roles SET gold = gold - ? WHERE id=? AND gold >= ?     → rowcount 必须 = 1
  ② 扣 B 的金币  同上
  ③ 加给 A        UPDATE roles SET gold = gold + ? WHERE id=?                    → rowcount 必须 = 1
  ④ 加给 B       同上
  ⑤ A 的物品全部过户给 B（一条 SQL 批量 ✓ 每件都要满足"还是他 + 还被这个会话锁着"）
       UPDATE items SET role_id=?, locked_by=NULL
        WHERE id IN (…) AND role_id=? AND locked_by=?                            → rowcount 必须 = 件数
  ⑥ B 的物品全部过户给 A（同上）
  ⑦ 两条 gold_log（A 出一进、B 出一进 —— ★ 一共 4 条，因为每人都有进有出 ✓）
  ⑧ INSERT INTO trade_log (…)                                                   → sid 撞主键就整笔回滚 ✓
RELEASE trade        ← 成功
  或
ROLLBACK TO trade    ← 任何一步 rowcount 不对 / 抛异常 ✓ 一个字都没写进去 ✓

然后（★ 无论在事务里还是外面）：
  self.inbox.put(('tradres', None, {'sid': sid, 'ok': True/False, 'why': '…'}))
  ↑ ★ 存档线程只【入队】✗ 不改任何世界状态 ✓ 铁律没破 ✓
    （和 post_save 反方向的一个队列 ✓ 同一个 queue.Queue ✓ 线程安全 ✓）
```

★ **为什么用 SAVEPOINT 而不是直接让整个 batch 一起回滚**：
`_run_saver` 是把攒了 0.5 秒的一批 SQL 放在**同一个** `with dbmod.db(cfg)` 里执行的 ✓
（`world.py:3195` ✓）—— 一批里可能还混着**别人的**移动存档 ✓
要是这一笔交易的失败把整批都炸了 ✗ 别人就白存了 ✓
→ `SAVEPOINT` 让**只有这笔交易**回滚 ✓ 其余照常提交 ✓

★ **为什么"先落库、后改内存"**（这条容易写反 ✗）：

```
错的做法：tick 线程先 p.gold -= 100 ✓ 再 post_save ✓
  → 万一事务失败了 ✗ 玩家看到钱少了 ✗ 但库里没少 ✓✓ 对不上 ✓

对的做法（本方案）：tick 线程改成 'settling' → post_save → 等 'tradres: ok' → 才改内存 ✓
  → 事务失败 = 内存压根没动 ✓ 两边永远一致 ✓
  → 代价：成交到"界面刷新"之间多一个落库往返（实测 < 100 毫秒 ✓ 感觉不出来 ✓）
    ★ 而且界面在 settling 状态显示"正在结算…"✓ 用户完全能接受 ✓
```

★ **崩溃窗口（诚实写）**：

```
窗口 A：post_save 之后、事务提交之前崩溃
  → 库里没变 ✓ 内存没了 ✓ 物品锁在重启时被清掉（§4.1 第 5 条 ✓）
  → 结果：交易没发生 ✓ 双方什么都没损失 ✓ 一致 ✓

窗口 B：事务提交之后、tradres 被 tick 处理之前崩溃
  → 库里【已经成交了】✓ 但玩家没收到"交易成功"的提示 ✗
  → 玩家重新登录：金币是新的 ✓（role_public 带 gold ✓ auth.py:135）
                  背包重新拉也是新的 ✓（/api/bag ✓ app.py:667）
  → 只是少了一条提示 ✓ 可接受 ✓
  ★ 这是经典的 at-least-once / at-most-once 取舍 ✗
    要做到"提示也不丢"就得再写一套补偿表 ✗ 本方案认为不值得 ✓（记在 §7 ✓）
```
