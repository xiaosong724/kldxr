## 1. 怎么跑

```
双击  启动服务器.bat          ← 开一个窗口，关掉窗口 = 停服
      停止服务器.bat          ← 或者用这个停
```

命令行也行：

```bash
cd server
python app.py                # 用 config.json（HTTP 8899 + WebSocket 8900）
python app.py --port 9000    # 临时改 HTTP 端口
python db.py                 # 只建库（幂等，可重复跑）
```

启动后控制台会打印本机地址和局域网地址：

```
网页      : http://127.0.0.1:8899/
游戏通道  : ws://127.0.0.1:8900/ws
手机用    : http://<局域网IP>:8899/   (ws://<局域网IP>:8900/ws)
健康检查  : http://127.0.0.1:8899/api/health
```

浏览器打开会看到**登录浮层** → 注册两个不同名字 → 两台设备各登一个 → 应该能互相看见。

**依赖**：只需 Python 3 标准库（零第三方包）+ Node.js（只有跑 JS 测试才需要）。
`启动服务器.bat` 里写死了一个 Python 路径，找不到会自动回退到 PATH 里的 `python` / `py -3`——
**换机器的话建议把那行改成你自己机器上的路径**。

## 3. ★ 三条不能破的规矩

### ① 线程纪律（方案 §13.5）

```
主线程        HTTP（静态页 + /api/*）
asyncio 线程  WebSocket：只做 ① 认证 ② 意图入队 ③ 快照下发
tick 线程     世界状态唯一持有者
存档线程      DB 写入
```

- **世界状态只允许 tick 线程读写** → 天生无锁竞争，不要给世界状态加锁
- **tick 线程绝不碰磁盘、不 await** → 一次 IO 就能让全世界卡住
- **网络线程绝不碰世界状态** → 只能入队（`World.post_intent`）
- 从 tick 线程往网络发消息，只能走 `World._to_net()`（内部是 `loop.call_soon_threadsafe`），
  **且每 tick 批量投递一次**，不是每个玩家一次

### ② 分层铁律（方案 §1.3）

```
web/core\       玩法 + 渲染    ★ 不许出现任何浏览器专有对象
web\platform\   画布/UI/网络/音频/存储
```

微信 / 抖音小游戏**没有浏览器 DOM**。core 保持干净，将来上小程序只换 `platform/` 一层。

**改完 core 必须跑**：`python tools\check_core_dom.py`（退出码 0 = 达标）

### ③ 服务端权威（方案 §1.4）

伤害 / 死亡 / 掉落 / 经验 / 装备 / 加点 **都由服务器算**，客户端只发意图。
位置目前是客户端算（服务器将来做抽查）——这是为了手感故意留的。

### P0-9 是怎么收口的（第 26 轮）

交接文档原来留了一个「改一行就能做」的判定实验（把 `replay()` 改成按发送时刻喂）。
做完的结论是：**喂键节奏不是元凶** —— C（到达时刻喂）和 C′（发送时刻喂）**都归零（0.0%）**。
那个「离线 σ=0、回放却 25%」的矛盾，出在**测试自己**的两处错误上：

```
① 钟差基准用【首包】估 off0 = recv[0].now − recv[0].t
   而首包往往是服务端重发的陈旧包（迟到能到 1 秒）→ off0 被抬歪
   → rt 被整体推到缓冲头之前 → 340/357 帧被"冻结" ✗
   （core 里本来用的是"热身期最小延迟"当基准，测试没跟上）
② 到达时刻在【批量循环】里取：同一批消息共用一个 now
   → 到达延迟实测 σ=135ms / 最大 858ms（真实值只有 σ≈13ms / 最大 35ms）
   → 假的迟到 → 假的抖动。真实客户端是在 onmessage 里取时刻的 ✓

改掉这两点，同一条产品链路：走路抖动 15.7% → 2.4%
```

顺手挖出并修掉的两个**真 bug**（详见 §5 的 #7 #8）：

```
#7 队友站住不动时，会被画到真实位置【前方 1.1 米】，一直停那儿，等他再动才弹回来 ✗
   根因：addOther 里"位置没变就不塞新包"（注释还写着"静止时也不会乱外推"）—— 是反的
   修法：位置没变也塞一个【保持包】（位置不变、时间前进）→ 缓冲尾跟着他的钟走 ✓
#8 抖动缓冲一变，渲染位置就【瞬间平移 v×Δdelay】（实测一帧跳 53mm → 单帧速度虚高 3.2m/s）✗
   修法：抽出 netRenderAt()，让 rt 用"略快/略慢的播放速度"去追目标（NET.rtCatch=0.1）
         —— 位置始终连续，代价只是零点几秒的轻微快慢 ✓
```

## 5. 已修的真 bug（别再犯，根因都记下来）

这几个都是 P0-9 的测试挖出来的，**只跑端到端永远看不到**：

| # | Bug | 根因 | 修法 |
|---|---|---|---|
| 1 | 服务端每次回 `pong` 都断线 | `protocol.pack(t, **d)` 的**形参名 `t`** 和消息体字段 `t` 撞了 → `TypeError: got multiple values for argument 't'` | 改成 `pack(mtype, **d)` |
| 2 | 一个慢客户端会卡住整个 tick | 广播是 `await` 逐个发；客户端不读 → TCP 缓冲满 → `drain()` 挂住 | 每连接一个发送队列 + 写协程；业务层只 push（同步），队列满丢最旧的帧 |
| 3 | 时钟校准被重复包污染 | 服务端每 tick 重发"当前状态"，对方不动时同一份 `(x, t)` 发很多次 → `t` 不变而 `localNow` 前进 → 迟到量虚增 | `netClkUpdate` 里挡掉 `remoteT` 没前进的包。**修前：最大迟到 1011ms、缓冲顶到 250ms 上限；修后：50ms / 95ms** |
| 4 | 间隔夹紧太窄 | `netPush` 把间隔夹到 `[0.7×, 1.4×]rate`（23~47ms），但服务端 30Hz 采样造成的**正常**间隔就是 40~70ms → 被夹 → 时间轴压缩 | 放宽到 `[0.4×, 6×]rate` |
| 5 | **外推被夹死 → 0 速度帧** | `netSample` 里 `if (u>1) u = Math.min(u, 4)`；渲染时刻越过缓冲尾时被夹住 → 位置不再前进 | 改成 `Math.min(u, NET.extrapMax||12)`。匀速运动外推本来是精确的，夹死反而制造"一顿一冲" |
| 6 | 自适应 delay 突变 | 渲染时刻 = 本地钟 − off − delay；delay 一变渲染时刻就跳 → 位置跳 → 速度尖峰 | delay 改成**不对称**变化：变大立刻、变小慢慢收（`NET.delayFall = 0.02`）。**后来发现只做了一半**：不对称仍然是瞬时平移 → 由第 8 条彻底解决 |
| **7** | **队友站住不动时，被画到真实位置【前方 1.1 米】** | `addOther` 里"位置没变就不塞新包"（注释还写着"静止时也不会乱外推"，**是反的**）→ 缓冲尾停住、渲染时刻越过它 → 按末段速度外推，直到 `extrapMax` 上限 | 位置没变也塞一个**保持包**（位置不变、时间前进；静止时半速塞）。`tools\diag_standstill.js` 离线复现：1100mm → 50mm |
| **8** | **抖动缓冲一变，渲染位置就瞬间平移** | `rt = 本地钟 − off − delay`；delay 一跳 rt 就跳，位置平移 `v×Δdelay`。实测一帧跳 17.6ms → 位置跳 53mm → 单帧速度虚高 3.2m/s → 抖动 8.8%（同数据固定 80ms 缓冲只有 1.0%）| 抽出 `netRenderAt()`：让 rt 用"略快/略慢的播放速度"追目标值（`NET.rtCatch = 0.1` = 播放速度最多偏 ±10%）→ 位置始终连续。**名义前进量要用真实经过时间，不能用 `frame()` 的 dt**（顿帧时 dt 会乘 0.2）|

### ★ 第 34 轮：攻击改成「正前方扇形」（P2 的第一刀）

**用户反馈**：*"攻击时应该是玩家面向那边砍的时候，会对那边造成伤害，而不是离得近都有伤害
—— 这样就算背对着僵尸也能打，不合理"* ✓ 完全同意，这是原来判定的真 bug：

```
老逻辑：在所有目标里挑【最近的那一个】，只要 dist ≤ ATK_RANGE(2.4) 就打 → 完全不看朝向 ✗
       结果：背对着僵尸也能砍到，正面站着 3 只只掉 1 只 —— 手感很怪 ✗

新逻辑：距离 ≤ ATK_RANGE  且  和朝向的夹角 ≤ ATK_ARC(1.05 弧度 ≈ 60°)
       两个条件都满足的【全打】→ 挥一刀扫正前方 120° 那一片 ✓ 才像"砍向那边"✓
```

实现要点：

- 新常量 `G.ATK_ARC = 1.05`（正前方 120° 扇形），和新函数 `inAtkArc(tx, tz)` ✓
- 朝向用 `P.yaw`（= `atan2(dx, dz)`，跟移动方向一致 ✓）—— 注意**夹角要绕回 [-π, π]**，不然跨 ±180° 时判定会反 ✗
- 贴脸（距离 < 0.01）**直接算命中** —— 否则算不出角度会把"骑脸砍"判成打不到 ✗
- 多个目标时：伤害先全摇好 → **音效/震动只出一次**（不然一刀砍 3 只叠 3 个音效很吵 ✗）

## 9. 注意事项 / 坑

1. **音效版权** ⚠️：`web/assets/sfx/` 里 31 个音效是**从 Minecraft 原版提取的**，自用没问题，
   **对外发布前必须换成原创音频**。

2. **★ 后台管理（第 48 轮）：`/admin`** ⚠️

   ```
   玩家不该有的能力全部搬到这个页面了（浏览器打开 http://127.0.0.1:8899/admin）：
     刷怪（可指定职业/等级、可清场）· 发武器 · 踢下线 · 治疗 · 全服喊话 · 看内部状态
   密码：server/config.json 的 admin_password（默认 xiuxian-admin）
   ★★ 对外开服前一定要改掉 ✗（默认值写在这份文档和 config 里，等于公开的）
   会话：登录后发一个内存 token，12 小时有效、重启即失效 ✓ 连续输错 8 次锁 5 分钟 ✓
   ```

   为什么要有它（这一轮的真实原因）：
   ```
   之前 WS 意图 spawn / giveweapon 是【任何玩家】都能发的 ✗
     → 改个包就能自己刷一堆怪、给自己发武器 ✗
   /api/health 还对着玩家吐"账号数/角色数/数据库路径" ✗
   现在：
     · 玩家端这两个意图【默认拒绝】（config 的 allow_player_debug=false ✓）
       要临时调试：把 allow_player_debug 改成 true（只该在本地开 ✓），或者直接用 /admin ✓
     · /api/health 只报"活着没 + 世界在不在跑"（online/tick/mobs/tickMs ✓）
     · 内部状态（账号数、角色数、最慢 tick、待存档…）只在管理页 ✓
   ★ 管理操作也是【只入队】→ 真正改世界状态的是 tick 线程 ✓（世界状态只有它能碰 ✓）
   ```

3. **`web/3d-v4.html` 是冻结的对照版本**，不要改它。所有开发都在 `index.html` + `core/` + `platform/`。

3. **`server_version = 'zombie-xiuxian/0.1'`** 是早期名字留下的，纯显示用，不影响功能。

4. **协议版本**：`protocol.py` 里 `PROTOCOL_VERSION = 1`。客户端版本对不上会被 `kick(ver)`——
   改协议记得同步这个号和 `web/core/game.js` 里的 `PROTO_VER`。

5. **`/api/health` 会报世界状态**，排查卡顿先看这里：
   ```json
   "world": {"online":2, "tick":267, "tickMs":0.12, "tickMaxMs":0.28,
             "dropped":0, "pendingSave":0, "inbox":0}
   ```
   `tickMaxMs` 顶到 33ms 就说明该优化了（以后加僵尸 AI 时重点看这个）。

6. **文件编码**：全部 UTF-8 **无 BOM**；`.py/.md/.json/.js/.html` 用 LF，
   `.bat` 用 **CRLF**（用了 LF 的批处理某些分支语句会出问题）。
   写 Python 脚本带 `# -*- coding: utf-8 -*-`，显式 `encoding='utf-8'`、`newline='\n'`。

7. **控制台是 GBK**，`app.py` 里已经 `sys.stdout.reconfigure(encoding='utf-8')`，
   配 `.bat` 里的 `chcp 65001`，所以控制台中文正常。

8. **服务端 30Hz 采样 + 客户端 30Hz 上报会"打架"**：实测约 15% 的上报被采样吃掉，
   接收端看到的键间隔变成 33~67ms 不匀。**这是已知结构性问题**——
   离线测试证明它不影响渲染平滑度（不匀的键照样能还原成匀速），但值得记着。
