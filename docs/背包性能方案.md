# 背包卡顿 · 体检报告与优化方案（round507）

> 用户："背包东西多了，一键整理和使用延迟特别高，是带宽不够还是配置不行？"

## 0. 结论先说

**不是配置不行，也不是带宽"不够" —— 是一次请求搬了 647 KB 没压缩的数据。**

服务器 CPU 完全没压力（整理 1420 件只要 **35 ms**），
问题在**下行流量**和**每次都全量重拉**。

---

## 1. 实测数据（本地，`fangou` 这个号 1420 件）

| 指标 | 数值 |
|---|---|
| 背包件数 | **1420 件** |
| `/api/bag` 返回的 JSON | **647.6 KB** |
| **同样的数据 gzip 后** | **25.7 KB（4%）** ← 25 倍 |
| 服务器 `bag_of()` 读库耗时 | **13.6 ms** |
| 服务器 `bag_sort()` 整理耗时 | **35.2 ms** |
| 每件装备 JSON 平均 | 456 字节（最大 1032 字节）|

### 换算成"玩家体感的秒数"（照着 647 KB 不压缩算）

| 云端上行 | 不压缩 | gzip 后 |
|---|---|---|
| 1 Mbps | **5.30 秒** | 0.21 秒 |
| 2 Mbps | **2.65 秒** | 0.11 秒 |
| 5 Mbps | **1.06 秒** | 0.04 秒 |
| 10 Mbps | 0.53 秒 | 0.02 秒 |

★ 腾讯云轻量常见就是 1~5 Mbps 上行 ✓ 正好落在"1~5 秒"这个区间 ✓
**这就是玩家感觉到的"延迟"** ✓

## 2. 三个真正的原因

### 原因 ① `/api/bag` **没有 gzip**（最大头，占 96% 的浪费）

`app.py` 里只有**静态文件**走了 gzip（`_send_static(gz=True)`），
`_send()` 这个 JSON 通道**从来没压过** ✗

背包 JSON 里全是重复的字段名（`"affixes"`、`"cooldown"`、`"itemLv"`…），
gzip 压缩率 **96%** ✓ 业界正常水平 ✓

### 原因 ② 每次"使用 / 脱下 / 整理"都**全量重拉**

`web.js` 里这三处都是：

```js
setTimeout(function(){ BAG.busy = false; bagFetch(bagRender); }, 420);
```

→ 一次穿装备 = **647 KB** ✗
→ 一次整理 = **647 KB** ✗
→ 打开背包 = **647 KB** ✗

而实际变化只有 **1~2 格**（穿上的那件 + 脱下来的那件）✓

### 原因 ③ 一键整理在服务端是 **N 条 UPDATE**

```python
for idx, rec in enumerate(items):
    c.execute('UPDATE items SET slot_index=? WHERE id=? AND role_id=?', ...)
```

1420 件 = 1420 条 UPDATE ✓ 实测 35 ms（**这条其实不慢** ✗ 列出来是因为顺手能优化）

## 3. 方案（按性价比排序）

| # | 做什么 | 收益 | 风险 | 工作量 |
|---|---|---|---|---|
| **1** | **给 JSON 接口加 gzip**（`/api/bag` 等）| **647 KB → 26 KB（-96%）** | 极低 | 小 |
| **2** | **使用/脱下不再全量重拉**：服务器 push 变化的那 1~2 格，客户端就地改 | 一次操作 **647 KB → 几百字节** | 低 | 中 |
| **3** | **整理完不再重拉**：客户端本地按同一套规则排序（或服务器返回轻量 id 数组）| 整理 **647 KB → 0** | 低 | 中 |
| 4 | 背包**分页**（一次 60 件 + "加载更多"）| 首屏 647 KB → 28 KB | 中（要改协议）| 中 |
| 5 | 整理改成**一条** SQL（CASE WHEN）| 35 ms → ~5 ms | 低 | 小 |
| 6 | 背包**瘦身**：`id`/`fx`/`ext` 这些客户端用不上的字段不传 | 647 KB → ~380 KB | 中 | 中 |

### 我建议第一批就做 1 + 2 + 3 + 5

做完之后：

```
打开背包   647 KB → 26 KB   （1 Mbps 下 5.3s → 0.21s）
使用装备   647 KB → ~1 KB   （几乎立刻）
一键整理   647 KB → 0       （本地排序，瞬间）
```

而且**不用改协议** ✓ 客户端也不用大改 ✓ 风险最低 ✓

### 第二批（如果还觉得慢）

- 分页（4）：首屏只拿 60 件
- 瘦身（6）：砍掉客户端不用的字段

## 4. 顺带发现的两个隐患

1. `bag_of(cap=2000)` 到 2000 件就**截断**了 ✗ 而且没有"还有更多"的提示 ✗
   → 挂机党迟早撞到（现在 1420 件，离 2000 不远了）
2. 云服务器上行到底多少，我没测过 ✗
   → 上面那张表是按 1/2/5/10 Mbps 算的 ✓ 待会儿我可以实测一次（下载 647 KB 计时）

## 5. 实施结果（round507 已上线）

### 5.1 做了哪几条

| # | 改动 | 结果 |
|---|---|---|
| 1 | **JSON 接口加 gzip**（`app.py _send`）| 实测 600 件：**248 KB → 3.1 KB**；1420 件：647 KB → 25.7 KB |
| 2 | **使用/脱下不再全量重拉**：服务器在 `weapon`/`armor` 消息里带 `iid`，客户端就地改那一格 | 一次穿装备 **647 KB → 0** |
| 3 | **整理不再重拉**：新增 `bagsortok {ids:[...]}`，客户端本地重排 | 整理 **647 KB → 0**（1420 件只发 9 KB 的 id 数组）|
| 5 | 整理 SQL 没动（实测 35ms 不算瓶颈 ✗ 留着以后再优化 ✓）| — |

★ 还留了**兜底**：穿装备后 2.5 秒内没收到服务器推送（掉包/断线），才退回老的整包重拉 ✓
★ `bag_of(cap=2000)` 的分页仍然没做（这批先不动协议 ✓ 见 §4 隐患）
