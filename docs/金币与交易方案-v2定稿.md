## 1. 金币（相对 v1 的差异）

- 存储、迁移、防负三层、线程纪律 **完全沿用 v1 §1**（`roles.gold INTEGER NOT NULL DEFAULT 0 CHECK(gold>=0)`）。
- **新增来源**：卖物品给系统（§3）。
- **新增上限逻辑**：

```
每次金币入账后：
    if gold > CAP:                       # CAP = 1_000_000_000
        n = (gold - CAP) // 100_000_000  # 能换几个黄金
        if n > 0:
            投递一条"加物品"到背包（黄金 × n）  # 走已有的发物品通路
            gold -= n * 100_000_000
        # 余数留在金币里，不丢 ✓
★ 金币永远 <= 10 亿 + 1 亿（一次入账最大量）✗ 不会溢出 ✓
★ 黄金是可堆叠物品 ✗ 离线也在库里 ✓ 也能被魔气夺取 ✓
```

- **黄金 → 金币**：玩家点"卖给系统" → 按 1 亿/个给你，**不扣税**（这是官方兑换口）。

## 2. ★ 交易所（取代 v1 的面对面交易）

### 2.1 与面对面方案的根本差别

| | 面对面（v1，作废） | 交易所（v2） |
|---|---|---|
| 双方 | 必须同时在线、5 米内 | ★ **不需要**（离线也能被买走） |
| 流程 | 双人状态机 + 双方确认 | ★ **单方上架，单方购买**（简单得多） |
| 距离校验 | 有 | ★ **没有** |
| 超时 | 60 秒无操作取消 | ★ 上架 **7 天**过期自动下架归还 |
| 安全重点 | 双方内容不一致、抢锁 | ★ **托管 + 单事务成交 + 幂等** |

### 2.2 数据表（新增 2 张 + 2 处改动）

```sql
-- 上架单：上架时物品从背包【移走】，托管在这里
CREATE TABLE IF NOT EXISTS listings (
  lid       INTEGER PRIMARY KEY AUTOINCREMENT,
  seller    INTEGER NOT NULL,              -- roles.id
  item_json TEXT    NOT NULL,              -- 托管中的物品（和 items 表同一格式）
  price     INTEGER NOT NULL CHECK (price > 0),
  ts        INTEGER NOT NULL,              -- 上架时间（now_ms）
  expire    INTEGER NOT NULL,              -- 到期时间（now_ms + 7 天）
  state     TEXT    NOT NULL DEFAULT 'on'  -- on / sold / cancelled / expired
);
CREATE INDEX IF NOT EXISTS ix_listings_state ON listings(state, price);

-- 成交流水（幂等 + 审计 + 管理端查询）
CREATE TABLE IF NOT EXISTS trade_log (
  sid       TEXT PRIMARY KEY,              -- ★ 幂等键（见 2.5）
  lid       INTEGER NOT NULL,
  seller    INTEGER NOT NULL,
  buyer     INTEGER NOT NULL,
  price     INTEGER NOT NULL,
  tax       INTEGER NOT NULL,
  item_json TEXT    NOT NULL,
  ts        INTEGER NOT NULL
);

-- 迁移 v5：一个玩家最多 N 件在售（查询用）
CREATE INDEX IF NOT EXISTS ix_listings_seller ON listings(seller, state);
```

### 2.3 状态机（只有 4 个状态，比 v1 简单）

```
上架 on ──买入──→ sold       （成交：扣买家钱 → 卖家得 95% → 物品进买家背包）
   │
   ├──卖家下架──→ cancelled  （物品原样归还背包）
   └──超 7 天───→ expired    （物品原样归还背包）

★ 归还时如果背包满了 → 不删上架单，留在 expired 状态，玩家清背包后点"领取"✓
★ 任何状态变化都由 tick 线程发起 ✗ 落库走 saver 线程 ✓
```

### 2.4 成交 = 一条事务（全部靠 rowcount 说话）

```sql
BEGIN IMMEDIATE;
-- ① 抢上架单（只有 state='on' 能被抢到；抢不到说明被别人买走了）
UPDATE listings SET state='sold' WHERE lid=? AND state='on';
-- rowcount 必须 = 1，否则整笔回滚（★ 这就是 TOCTOU 防护）

-- ② 扣买家金币（不够就扣不到）
UPDATE roles SET gold = gold - ? WHERE id=? AND gold >= ?;
-- rowcount 必须 = 1，否则回滚（★ 买家没钱）

-- ③ 卖家收钱（扣 5% 税）
UPDATE roles SET gold = gold + ? WHERE id=?;   -- ? = price - tax

-- ④ 记流水（sid 主键 → 重复提交会撞 UNIQUE，整笔回滚 ✓ 幂等）
INSERT INTO trade_log(sid, lid, seller, buyer, price, tax, item_json, ts) VALUES(...);

-- ⑤ 物品进买家背包
INSERT INTO items(...) VALUES(...);
COMMIT;
```

★ 卖家**离线**也能收钱（直接改 roles 行 ✓ 他下次上线就是新余额 ✓）。
★ 卖家收钱后可能**超过 10 亿** → 黄金转换在 tick 线程入账时做（§1）✓

### 2.5 幂等键 sid（★ 不能用进程内自增）

```
★ v1 已发现：'t1' 这种自增键重启后会撞主键 ✗ → "重启一次以后再也交易不了" ✓
正解：sid = 't' + 服务器启动毫秒 + '.' + 进程内自增序号
```

### 2.6 上架/购买/下架接口

| 方向 | 消息 | 字段 | 说明 |
|---|---|---|---|
| C→S | `mklist` | `iid`（物品 id）, `price` | 上架（校验归属/未装备/未锁/价格>0/在售数<上限） |
| C→S | `buyitem` | `lid`, `sid` | 购买（幂等键由客户端生成 ✗ 服务器也校验） |
| C→S | `unlist` | `lid` | 下架 |
| C→S | `lists` | `page`, `sort`, `q` | 浏览（分页 20/页 ✗ 排序：价格/时间/阶数 ✓ 可按阶数/类型筛选） |
| C→S | `mylists` | — | 我的上架（含 expired 待领取） |
| S→C | `listres` | `ok`, `msg`, `lid` | 上架/购买/下架的结果 |
| S→C | `listpage` | `rows[]`, `total`, `page` | 浏览结果 |

### 2.7 限流与防刷

| 项 | 值 | 理由 |
|---|---|---|
| 一个玩家在售上限 | **10 件** | 防塞满交易所 |
| 上架费 | ★ **收 1%（不成交不退）** | 防刷屏（挂 1 金币的垃圾也没意义） |
| 最低上架价 | **10 金币** | 配合上架费 |
| 购买自己的东西 | **禁止** | 防刷税/刷流水 |
| `mklist` 限流 | 10 次/分钟 | 沿用现有 `RATE_LIMIT` |
| 大额上弹幕 | >10000 金币 或 ≥7 阶 | ★ 反 RMT 的唯一手段（用户默认同意 ✓） |

## 3. ★ 物品价值（系统收购价）

### 3.1 公式

```
【装备】价值 = 基础价[阶] × (1 + 物品等级/40) × 类型系数 × 状态系数 × 附加属性加成
   基础价： 1阶10 · 2阶30 · 3阶100 · 4阶300 · 5阶800
            6阶2500 · 7阶8000 · 8阶25000 · 9阶80000     （约 ×2.8/阶）
   类型系数：武器 1.2 · 防具 1.0 · 饰品 1.1
   状态系数：完好 1.0 · ★破损 0.3
   附加属性：每条 +15%

   例：60 级 5 阶完好武器 = 800 × 2.5 × 1.2 = ★ 2,400 金币

【材料/消耗品】价值 = 基础价[稀有度] × 数量
   常见 2 · 少见 10 · 稀有 60 · 史诗 300 · 传说 1,500

【黄金】价值 = 1 亿（卖给系统即换回金币，不扣税）
```

### 3.2 代码放哪（★ 关键：不能查库）

```
新建 server/value.py ✗ 纯 Python 字典（零依赖 ✗ 零 IO ✓）
   def value_of(item) -> int      # 从 item 的 json 里读 tier/lv/kind/rarity/broken
★ 为什么不做成数据库表：tick 线程不许做磁盘 IO ✓
   （价格是【不变的规则】✗ 写死在代码里最安全 ✗ 改价要重启 ✗ 可接受 ✓）
★ 材料稀有度从 drops.py 现有的定义读 ✗ 不另建一套 ✓
```

### 3.3 ★ 经济铁律（上线后要盯的数）

```
① 系统价 ≈ 交易所成交价的 30%
   → 盯"系统收购总量 ÷ 交易所成交量"：超过 3:1 说明系统价高了 ✗ 下调 ✓
② 金币回收口：5% 交易税 + 1% 上架费 + 复活 + 传送 + 洗点 + 黄金沉淀
   → 盯"总金币存量"的月增长率 ✗ 超过 +30%/月 就要加回收 ✓
```

## 7. 测试清单（关键 20 条 ✗ 完整版沿用 v1 §6 的 44 条思路）

**正常流程**
1. 上架 → 别人能看到 → 买走 → 双方余额正确（卖家得 95%）
2. 下架 → 物品原样归还（阶数/耐久/附加属性都不变）
3. 7 天到期 → 自动下架并归还
4. 卖给系统 → 金币 += §3 公式值 ✗ 物品消失
5. 黄金卖系统 → 金币 += 1 亿

**边界**
6. 背包满时取回到期物品 → 不丢 ✗ 留在待领取 ✓
7. 价格 = 最低价 10 ✗ 上架费 1%（至少 1 金币 ✓）
8. 在售 10 件时再上架 → 拒绝
9. 金币刚好 10 亿 ✗ 再收入 → 转 1 黄金
10. 余额刚好等于价格 → 能买（`gold >= price` ✓）

**恶意/并发**
11. 同时两笔买同一件 → 只成一笔 ✗ 另一笔拿回钱 ✓
12. 同一 sid 重复提交 → 只扣一次
13. 买自己的东西 → 拒绝
14. 上架已装备/已锁/不属于自己的物品 → 拒绝
15. 价格传负数/0/超大数 → 拒绝
16. 余额 100 买 101 的 → rowcount=0 ✗ 回滚干净
17. 上架后物品还在背包里 → 不允许（托管必须移走）
18. 卖家离线时被买走 → 他下次上线余额已增加
19. 上架费扣了但不成交 → 不退（且不会重复扣）
20. 服务器崩溃重启 → `locked_by` 全清 ✗ 上架单仍在 ✓ 可继续买
