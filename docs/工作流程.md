# 改代码 → 上线的工作流程（★ 必须遵守）

> 起因：第 207 轮我在云端上线了自动战斗 ✗
>   用户原话："不是说让你在本地做完了我确认后再同步吗"
>   —— 我在本地测过了 ✓ 但【测完没等确认就传上去了】✗
>   这是流程问题 ✗ 不是技术问题 ✓ 所以写成文件钉在这里 ✓

## 铁规矩（三步，不许跳）

```
第一步  本地做 + 本地测
          · 服务器跑在本地（127.0.0.1:8899）
          · 用 headless 浏览器真跑一遍（不是"看着像对"✓ 要看数据 ✓）
          · 截图/读数值留证据

第二步  ★ 停下来，向用户报告 + 等确认 ★
          · 报告：改了什么 / 本地测出来什么 / 可能影响什么
          · 明确问一句："可以同步到云端吗？"
          · ★ 用户没明确说"可以"，就【不许】碰云端 ✗✗

第三步  确认后才同步
          · 同步必须：先停服务 → 复制 → 再起服务
            （第 196 轮的教训：边跑边传，玩家会看到半个页面 ✓）
          · 同步后再从外网验一次 ✓
```

## 为什么这条对（不是形式主义）

```
· 云端现在是【朋友在玩的正式服】✗ 不是我的试验场 ✓
  我传一次 = 可能把正在玩的人踢下线 / 弄坏存档 / 造成维护页 ✓
· 已经出过两次事：
    第 196 轮：边跑边传 → 用户看到 "SETCFG is not defined" ✓
    第 207 轮：停服务重启 → TIME_WAIT 卡住 → 服务起不来 ✓
· 本地随便折腾 ✓ 云端要稳 ✓ 两件事必须分开 ✓
```

## 具体的"不许"

```
✗ 不许"顺手就传了"（哪怕是修 bug ✓ 也要先问 ✓）
✗ 不许在用户玩的时候停服务（除非用户说可以 ✓）
✗ 不许因为"本地测过了"就省略第二步 ✗ 本地测过只是【第二步的前提】✓
✗ 不许把"我以为他会同意"当成同意 ✓
```

## 本地测试的标准动作（第一步怎么做才算数）

```
1. 本地起服：cd server && python app.py
2. headless 真客户端连 127.0.0.1 ✓ 走完整流程：
     登录 → 进世界 → 操作 → 读数值（不是只看页面有没有报错 ✓）
3. ★ 测试脚本自身也要检查一遍：
     最近三次"以为是功能坏了、其实是测试写错了"✓
     （顶层 return 语法错误 / 查错 DOM 元素 / 锚点转义 ✓）
     → 断言失败时，先怀疑自己的测试 ✓ 再怀疑代码 ✓
4. 报数据（不是报"感觉好了"✓）：改前/改后的具体数值 ✓
```
