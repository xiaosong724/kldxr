## 1. 目标与范围

### 1.1 这个系统要解决什么

```
现在：升级只涨"固有属性"（方案 §4.5，纯等级决定）✗
      → 所有 100 级的人一模一样 ✗ 没有 build ✗ 没有取舍 ✗
要做：每级发 3 点，玩家自由分配 → 同样是 100 级，两个人的号完全不同 ✓
```

### 1.2 v1 的范围（明确划线，防范围膨胀）

```
✓ 做：
   · 12 个属性全部【可以加点、可以存、可以在界面看到】
   · 其中 6 个【立刻生效】（有现成的消费点）
   · 加点 / 洗点 / 属性页展示 / 落库 / 重进保留
   · 与装备词条同一套"有效值封顶"规则（不会出现无敌号）

✗ 不做（明确写出来）：
   · 天赋树 / 前置依赖 / 分支专精 —— 方案里就没设计 ✗ 不加 ✗
   · 天赋道具（洗点丹）—— 见 §3.4，v1 用免费洗点代替 ✓
   · 暴击/闪避/命中/穿透/免爆/法力的【实际战斗效果】
     —— 它们要等 PvP 和法术技能 ✗ 现在没有消费点 ✗
     v1 只做"能加、能存、能看"，界面上明确标"待 PvP 开放"✓ 不骗人 ✓
```

## 2. 属性总表（12 个 · 精确换算）

> ★ 三类的"1 点"不是一回事 —— 这是最容易混的地方 ✗

### 2.1 对抗类（1 点 = 0.5%，成对相减）

| 属性 | key | 1 点 = | 有效值上限 | 对抗方 | v1 生效？ |
|---|---|---|---|---|---|
| 减伤 | `dr` | 0.5% | **50%** | 穿透 | ✓ 生效 |
| 穿透 | `pen` | 0.5% | 无 | 减伤 | ✗ 待 PvP |
| 暴击 | `crit` | 0.5% | **30%** | 免爆 | ✗ 待 PvP |
| 免爆 | `anticrit` | 0.5% | 无 | 暴击 | ✗ 待 PvP |
| 闪避 | `dodge` | 0.5% | **30%** | 命中 | ✗ 待 PvP |
| 命中 | `hit` | 0.5% | 无 | 闪避 | ✗ 待 PvP |

### 2.2 增益类（1 点 = 1%，没有对抗方）

| 属性 | key | 1 点 = | 有效值上限 | v1 生效？ |
|---|---|---|---|---|
| 爆伤 | `critdmg` | 1% | **+100%**（总 250%） | ✗ 待暴击实装 |
| 移速 | `speed` | 1% | **+60%** | ✓ 生效（客户端） |

### 2.3 池 / 强度类（点数直接换数值）

| 属性 | key | 1 点 = | 上限 | v1 生效？ | 为什么是这个数 |
|---|---|---|---|---|---|
| 血量 | `hp` | **+8** 点生命 | 无 | ✓ 生效 | 满级 300 点全投 = +2400；10 阶防具给 +530 → 天赋应该是装备的几倍 ✓ 但不能压过等级本身（100 级固有约 8300）✓ |
| 攻击力 | `atk` | **+1** 点攻击 | 无 | ✓ 生效 | 满投 = +300；100 级固有攻击约 1110 → 约 27% ✓ 明显但不失衡 ✓ |
| 法力 | `mana` | +4 点法力 | 无 | ✗ 待法术技能 | 和技能系统一起定（§6 会用到 `scale: mana`）|
| 灵气 | `qi` | +2 点灵气 | 无 | ✗ 待技能系统 | 现在是"蓝条"占位，做了技能才有意义 |

### 2.4 关键规则：上限只管「有效值」，投入点数**无上限**

```
闪避%     = 闪避点 × 0.5%                      ← 想加多少加多少 ✓
有效闪避% = clamp(闪避% − 命中%, 0, 30%)        ← 只有这里封顶 ✓

用户举的场景（这是设计意图，不是 bug ✓）：

  情形      闪避点   闪避%   对方命中   有效闪避
  正常        60     30%       0         30%（到顶）
  被针对      60     30%      20(10%)    20% ↓
  反针对      80     40%      20(10%)    30%（又满）
  军备竞赛    80     40%      60(30%)    10% ↓
```

→ **界面上必须同时显示"原始值"和"有效值"** ✗
否则玩家堆到 40% 却看到 30%，会以为点数白花了 ✗

## 3. 点数经济

### 3.1 发放

```
每级 +3 点 ✓ 从 1 级开始（1 级就有 3 点 ✓ 让新号立刻能玩到天赋 ✓）
100 级 = 300 点 ✓
```

### 3.2 ★ 免费点数 = 等级×3 − 已投入（**推导值，不单独存**）

```
free = level * 3 - sum(所有已投入点数)

★ 为什么不直接把 free 存在 roles.talent_free 里当准？
  那个字段已经有了 ✓ 但"存一个可以被推导出来的数"迟早会不一致 ✗
  （掉线重连 / 后台改级 / 数据库手改 → 立刻对不上 ✗）
→ 数据库里 roles.talent_free 保留（老代码在用 ✓），但**每次都以推导值为准**✓
```

### 3.3 老号怎么办（向后兼容）

```
不用做数据迁移 ✓ 推导公式天然兼容：
   老号没有任何天赋点记录 → sum = 0 → free = 等级 × 3 ✓
   一进游戏就有 300 点可花（100 级）✓
★ 这是"用推导代替存储"最爽的地方 ✓ 零迁移 ✓
```

### 3.4 洗点（v1 简化版）

```
方案原文：洗点消耗道具
v1 实际：免费洗点，但加 5 分钟冷却 ✓
理由：洗点道具还没实装 ✗ 而"加了点不能改"会让玩家不敢试 ✗
      → 先免费（有冷却防连点）✓ 道具做好后改成消耗 ✓
冷却存哪：内存（Player.resetT）✓ 不落库 ✓（重启就清，无所谓 ✓）
```

## 4. 生效规则（怎么算进最终数值）

```
① 采集：天赋点 → 各属性的"原始值"
② 对抗相减：有效% = clamp(我方% − 对方对应%, 0, 该项上限)
③ 池/强度类直接相加：有效值 = 固有 + 天赋 + 装备词条
④ 与装备词条的先后：先全部相加，再统一过一次上限 ✓
   （不能各自封顶 ✗ 否则"装备顶满 + 天赋顶满"会算出超过上限的值 ✗）
```

**具体到六条对抗的配对表**（实装时照抄 ✓）：

| 我方 | 被谁抵消 | 上限 |
|---|---|---|
| 减伤 `dr` | 攻击者的 `pen` | 50% |
| 暴击 `crit` | 目标的 `anticrit` | 30% |
| 闪避 `dodge` | 攻击者的 `hit` | 30% |
| 穿透 `pen` | （无上限，专门用来抵消减伤） | — |
| 免爆 `anticrit` | （无上限） | — |
| 命中 `hit` | （无上限） | — |

## 6. 数据模型

### 6.1 数据库（**表已经存在，不用改结构** ✓）

```sql
-- 已存在 ✓（server/db.py 第 58 行）
CREATE TABLE IF NOT EXISTS talents (
    role_id  INTEGER NOT NULL,
    stat     TEXT    NOT NULL,          -- 'hp' / 'atk' / 'dr' / ... 见 §2
    points   INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (role_id, stat)
);

-- 已存在 ✓（roles.talent_free）
--   ★ 保留字段，但计算一律用 §3.2 的推导值 ✓
```

### 6.2 内存（tick 线程独占）

```python
# Player.__slots__ 新增
'tal'          # dict: {'hp': 30, 'atk': 12, ...} 只放 points>0 的
'talCache'     # dict: 算好的原始值 {'hp': 240, 'dr': 15.0, ...}
'talDirty'     # bool: 有没有未落库的改动
'resetT'       # float: 上次洗点时间（做冷却）

# 线程纪律（铁律，别破）：
#   tick 线程【只读内存】✓ 加点是走 intent ✓ 落库交给 saver ✓
#   绝不在 tick 里碰 DB ✗
```

### 6.3 落库时机

```
加点 / 洗点 → 立刻 post_save（改一行或删几行）✓
  原因：加点不是高频操作 ✓ 丢了最让人恼火 ✗ 值得立刻写 ✓
（对比：耐久是攒 50 次才写 ✓ 那个是高频 ✓ 策略不同 ✓）
```

### 6.4 缓存失效

```
只要 tal 变了 → talCache 置空 ✓ 下次取用时重算 ✓
不要"改一个属性只更新那一项"✗ 对抗相减是跨属性的 ✓ 会算错 ✗
```

## 7. 协议（字段级）

### 7.1 客户端 → 服务器

```json
{"t":"talent","d":{"op":"add","stat":"hp","n":10}}
{"t":"talent","d":{"op":"reset"}}
```

```
字段     类型     约束
op       str     'add' | 'reset'（其它值 → 静默忽略 ✓ 不报错刷屏 ✗）
stat     str     必须在 §2 的 12 个 key 里 ✓ 白名单校验 ✗（防刷不存在的属性 ✓）
n        int     1 ~ 50 ✓（点一下 +1 ✓ 长按 +10 ✓ 上限 50 防一次刷爆 ✓）
                 ★ 三个校验缺一不可：白名单 / n 范围 / n ≤ 当前免费点数 ✓
```

### 7.2 服务器 → 客户端

```json
{"t":"talents","d":{
   "free": 187,
   "pts": {"hp":30,"atk":12},
   "raw": {"hp":240,"atk":12,"dr":15.0},
   "eff": {"dr":15.0,"speed":0,"crit":0},
   "live": ["hp","atk","dr","speed"]
}}
```

```
free  剩余可分配点数（推导值 ✓）
pts   已投点数（只含 >0 的项 ✓ 省带宽 ✓）
raw   各项原始值（界面显示"原始值"用 ✓）
eff   过完上限/对抗之后的**有效值**（界面显示"有效值"用 ✓）
live  哪些 key 在 v1 真正生效 ✓（界面据此标"待 PvP"✓）

★ 什么时候发：
   · 加点/洗点成功后立刻发 ✓（回执 + 新状态一起 ✓）
   · 进世界时发一次 ✓（登录/重进要能看到 ✓）
   · 升级时不用单独发 ✗ free 会变 ✓ 所以【升级时也发一次】✓
   ★ 漏了升级这次推送 → 玩家升了级界面还是 0 点可加 ✗ 这个坑必踩 ✓
```

### 7.3 限流

```
照抄组队那套（party_rate ✓）：10 次 / 10 秒 ✓
超了静默丢弃 + 回一条 notice「点太快了」✓
为什么要：加点是"按住 +10"✗ 很容易几百条/秒 ✗ 不挡会打满 tick ✓
```

## 9. 边界与异常

| 情况 | 处理 |
|---|---|
| 加点时正好升级 | 两边都改 free ✓ 以服务器【推导值】为准 ✓ 不会算错 ✓ |
| 两个人同时给一个号加点（同账号双开） | 后到的按最新 free 校验 ✓ 不够就拒绝 ✓ 不出现负数 ✓ |
| 客户端显示的 free 和服务器不一致 | 一律以服务器回执覆盖 ✓（客户端不自己算 free ✗） |
| 数据库里 talents 有未知 stat（改过版本） | 读的时候过滤掉未知 key ✓ 不崩 ✓ 但**不清库** ✓ |
| points 为 0 的行 | 读的时候跳过 ✓ 洗点时删掉 ✓ 不留垃圾行 ✓ |
| 数值溢出 | atk/hp 用 int ✓ dr 等用 float 保留 1 位 ✓ 理论最大值远小于溢出 ✓ |
| tick 线程里访问 tal | 只在 `_hp_max` / `_mob_bite` / 攻击结算三处读 ✓ 不写 ✓（写只发生在 intent 处理里 ✓ 那也是 tick 线程 ✓ 天然串行 ✓） |
| 洗点冷却期间再点 | 回 notice「还得等 X 秒」✓ 不静默 ✗ |

## 附：和"技能系统"的关系（别搞混）

