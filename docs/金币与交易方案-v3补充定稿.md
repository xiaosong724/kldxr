## §1 ★★★ 金币的权威副本（最重要的一条）

**结论：`Player.gold`（内存）是唯一权威 ✗ 数据库只是它的存档。**

理由：tick 线程不许做磁盘 IO（架构铁律）✗ 而打怪掉金币发生在 tick 里 ✓
如果"打怪改内存 ✗ 交易改库"两条路并存 ✗ 会互相覆盖 ✓✓

```
【规则】
① 所有金币变更【只改内存】Player.gold
   —— 打怪 / 卖系统 / 交易 / 复活 / 传送 / 洗点 / 管理端，全部走同一个函数：
      def _gain_gold(self, p, n, why):     # n 可为负
          # ① 扣钱时先判够不够（不够就 return False ✗ 绝不透支）
          # ② 加钱时判上限 → 溢出转黄金（§2）
          # ③ 记一笔内存流水（环形缓冲，最多 200 条，供管理端/排查）
          # ④ ★ 不写库！落库交给定时存盘 ✓
② 落库：沿用现有【定时存盘】（world.py 已有 533 行附近的周期存盘 ✓）
   + 关键节点立即入队：下线前 / 交易成交后 / 大额变更（>=10万）
   ★ 落库是【整份覆盖】`UPDATE roles SET gold=? WHERE id=?`
     —— 因为内存是权威 ✗ 不需要累加 ✓ 天然幂等 ✓
③ ★ 交易成交也不再直接 UPDATE roles 加钱/扣钱
   → 改成：扣/加内存 Player.gold ✗ 然后投递一条 SQL 只改【上架单状态 + 流水 + 物品归属】
   → 为什么要改：v2 §2.4 那条"扣买家 roles.gold"会和内存打架 ✓✓
④ 离线玩家的钱（卖家不在线）：交易时他不在内存 ✗
   → ★ 成交后给他写一条【待入账】（数据库 pending_gold 表 ✗ 或直接 UPDATE roles）
   → 他下次上线时 tick 线程读出来加进内存 ✓（§3）
```

## §3 离线玩家的钱（pending_gold）

```sql
CREATE TABLE IF NOT EXISTS pending_gold (
  id     INTEGER PRIMARY KEY AUTOINCREMENT,
  role   INTEGER NOT NULL,
  amount INTEGER NOT NULL,          -- 可为负（例如他被扣钱时不在线 ✗ 极少见）
  why    TEXT    NOT NULL,          -- 'trade_sell' / 'admin' ...
  ts     INTEGER NOT NULL,
  done   INTEGER NOT NULL DEFAULT 0 -- 0=未入账 1=已入账
);
CREATE INDEX IF NOT EXISTS ix_pending_role ON pending_gold(role, done);
```

```
★ 上线时（进世界那一刻 ✗ 和 _party_on_rejoin 同一个注入点 ✓）：
   读 pending_gold where role=? and done=0
   → 逐条 _gain_gold() ✗ 标 done=1 ✓
   → ★ 这一步要投一条 SQL 标记 done ✗ 走 saver ✓
★ 为什么不用"直接改 roles.gold"：那样离线收入会【绕过上限和黄金转换】✓✓
```

-- ★ 前 20 页用 OFFSET ✗ 之后切游标 ✓（几千件时体验一致 ✓）

-- 我的上架
SELECT lid, price, state, expire FROM listings WHERE seller=? AND state!='cancelled' ORDER BY ts DESC;

-- 在售数量（上架前校验 <10）
SELECT COUNT(*) FROM listings WHERE seller=? AND state='on';

-- 到期清理（tick 线程每 30 秒一次 ✗ 只 SELECT ✗ 状态改内存 ✗ 落库异步）
SELECT lid, seller, item_json FROM listings WHERE state='on' AND expire <= ? LIMIT 50;
