# 画面与客户端性能 · 方案 v2（不降画质，还要提画质）

> 2026-10-18 · 用户要求（原话）：
> **"不降低画质的情况下优化帧数，并且还需要提高画质；优化多实体战斗的帧数表现"**
>
> → 所以这版方案**删掉了**上一版的「动态分辨率 / 默认关阴影 / 自动降档」。
>   本版铁律：**任何优化都不许让画面变差**；省下来的预算**全部拿去提画质**。
>   所有数字来自 `tools/perf_probe.js`（画质档对比）、`tools/perf_stress.js`（怪数压测）、
>   `tools/perf_deep.js`（阴影投影体 / 包大小 / 解析成本）。

---

## 0. 结论（先看这个）

多实体战斗的帧数瓶颈**不是三角形**（40 只怪才 3 万三角形，太少了），而是**绘制调用（draw call）**，
而且被**两遍**放大：

```
主渲染 pass   304 次绘制   ← 其中 200 次是 40 只怪 × 5 个网格
阴影 pass     241 次绘制   ← 所有 castShadow 的网格再来一遍（只看得到 40 只怪就 200 次）
                        ↑ 阴影 pass 和主 pass 一样贵
```

**只要把"每只怪 5 次绘制"变成"1~2 次"，两遍一起省**：
40 只怪从 **545 次（304+241）→ 约 160 次**（-70%），而且**画质不降**——
因为合批后我们有预算把**角色阴影分辨率从 2048 提到 4096**、给怪加**每只独立的颜色/装备差异**。

**这一版的主线就三条**：
1. **怪 → 实例化合批**（主 pass 与阴影 pass 同时下降）
2. **阴影体系升级：静态烘一次 + 动态单独一张**（更快，而且角色阴影更锐利 = 画质提升）
3. **静态道具按块合并 + 贴图图集**（材质切换 67 → 20 以内，绘制 167 → 约 20）

## 2. 方案 A（核心）：怪从 5 draw → 1~2 draw

### 现状
```
每只怪 = 1 个合并身体（MOB_GEO 按职业缓存 ✓）
       + 4 条肢体（腿L/腿R/臂L/臂R，各自独立 Mesh，为了能摆）
       = 5 个 Mesh × 2 遍（主 + 阴影）= 每只怪 10 次绘制
```

### A1 肢体改 InstancedMesh（主 pass 立刻降）

- 按「肢体类型」分桶：`腿/臂 × 粗细 × 颜色` → 每个桶 1 个 `InstancedMesh`
- 每帧只写实例矩阵（`setMatrixAt`）——40 只怪 × 4 肢 = 160 个矩阵，CPU 成本 < 0.1ms
- **绘制调用：160 → 约 8**（桶的数量）
- **阴影 pass 同步受益**：InstancedMesh 一次绘制整个批
- 受击闪白：现在靠克隆材质 ✗ → 改成 `instanceColor`（InstancedMesh 自带，per-instance 颜色）
- 倒地动画：现在是整体旋转 ✓ 不受影响

**风险**：每只怪的肢体独立旋转要写矩阵（现有 `rotation.x` 逻辑照搬，只是改成矩阵合成）。
**预计**：40 只怪 主 pass 304 → **约 150**，阴影 241 → **约 90**。

### A2 远处怪改用「静态合并 LOD」（★ 已按实测修正）

> 用户问："不画腿会不会影响观感？"
> **实测答案：会。** 真实相机投影（512×746 屏幕）：
>
> | 距离 | 怪的屏幕高度 | 腿宽 | 腿高 |
> |---|---|---|---|
> | 20 m | 约 34 px | 约 5.8 px | 约 19 px |
> | **22 m** | **约 36 px** | **约 6 px** | **约 20 px** |
> | 30 m | 约 40 px | 约 6.8 px | 约 22 px |
>
> → 一条 6px 宽、20px 高的缺口，**看得出来** ✗
> 所以 "22 米不画腿" 这条**废掉**，改成下面这个：

**做法：远处换一个「不动的合并模型」（腿还在 ✓）**

| 距离 | 画什么 | draw | 观感 |
|---|---|---|---|
| < 18 m | 身体 + 4 条肢体（会摆动） | 5 | 完全一样 |
| 18~34 m | **合并成 1 个网格**：身体 + 四肢在一个固定姿态里一起合并 | **1** | **腿还在**，只是不摆了（这个距离上摆臂只有 1~2px，看不出 ✓） |
| > 34 m | 不画（现有视野剔除已经在做 ✓） | 0 | 和现在一样 |

★ 为什么这个方案更好：
① 形状一模一样（腿的轮廓都在）——只是"4 个独立网格 + 摆动"变成"1 个网格 + 不动"
② 合并后的网格可以**按职业预先算好**（和现在的 `MOB_GEO` 一个路子）→ 零运行时成本
③ 阴影 pass 同样 5 → 1（而且影子里腿还在 ✓）

★ 关键区别：18 米外的**摆臂幅度**在屏幕上只有 1~2px，停不停看不出 → 可以省
　而**腿的形状**少一条会缺 6px×20px → 不能省 ✓

**预计**：40 只怪里约 25 只在 18 米外 → 主 pass -100 次，阴影 -100 次（和原计划省得一样多 ✓）

★ 实施后要做 A/B 截图对照（同一个怪、同一位置、LOD 开/关），确认肉眼无差再合入。

### A3 屏幕外不更新动画（CPU 侧）

- 屏幕外（投影落在视口外 + 1 屏）：**跳过肢体矩阵计算**，只保留位置插值
- **预计**：40 只怪时 CPU 每帧省 0.2~0.5ms（手机更重要）

## 3. 方案 B（核心）：阴影体系升级 —— 更快 + 更清晰

### 现状（贵且租）
```
一张 2048² 阴影图，把【所有】castShadow 的网格都渲一遍（40 只怪 = 241 次绘制）
每 2 帧更新一次 → 角色移动时阴影会"跳"
```

### B1 拆成两张图：静态 + 动态

| 图 | 内容 | 更新频率 | 分辨率 |
|---|---|---|---|
| 静态阴影图 | 树 / 石头 / 墙 / 建筑（**位置永不变**） | **只烘一次**（或玩家移动 1 格时重烘） | 2048² |
| 动态阴影图 | 玩家 / 怪 / 掉落物 | 每帧（或每 2 帧） | **4096²**（只渲角色 → 承受得起） |

**收益**：
- 阴影绘制：241 → **约 60**（40 只怪的 50 次批 + 静态 0 次）
- **画质提升**：角色/怪的阴影从 2048² 提到 **4096²**，边缘更锐利（这正是现在最"糊"的地方）
- 动态阴影每帧更新 → 走路时影子不再"一跳一跳"（现在是每 2 帧）

**实现要点**：
- three.js 一个 `DirectionalLight` 只能挂一张 shadow map ✗ → 用**自制两遍渲染**：
  ① 把静态物件渲进一张 `WebGLRenderTarget`（正交相机，颜色 = 阴影深度）
  ② 主 pass 的 shader 里采样两张图取 min（`onBeforeCompile` 注入）
  - 或者更简单（推荐先做）：静态物件用**烘焙的 AO 贴花**（地面上一块半透明黑），动态只留真阴影
- 这条改动最大，放 P1 的后半

### B2 阴影相机紧贴视野（免费提清晰）

现在阴影正交相机范围可能比视野大 → 每 texel 覆盖的面积大 → 糊。
把范围收到"视野 + 10 米"，2048² 的清晰度直接翻倍。**零成本、纯画质提升**，先做。

## 4. 方案 C：静态道具合批 + 图集（材质切换 68 → 20）

### 现状
- 每块地形里的树/石头/墙是**各自独立 Mesh**（367 个网格里约 167 个是道具）
- 材质按名字分（草/土/石/砖/木…），40 只怪时唯一材质 68

### 做法
1. **按块合并**：一块 32×32 里的所有道具，按"材质"分组合并成一个 `BufferGeometry`（`mergeGeometries`）→ 每块 2~3 次绘制（现在一块几十次）
2. **图集**：把 10 张 32×32 贴图打进一张 256×256 图集 → 所有不透明道具共用 **1 个材质** → 每块 1 次绘制
3. 顺带 **假 AO**：合并时按"邻接/高度"给顶点色乘 0.75~0.9 → **画质提升**（现在方块全是平的）

**预计**：道具绘制 167 → **约 25**；唯一材质 68 → **约 20**。
**风险**：合并后单块的"单个道具受击闪白/消失"要改成"顶点色/整块重烘"（砍树时重烘一块，32 格重烘约 2~3ms，可接受）。

## 12. 服务器侧性能（实测 + 方案）

> 用户："从服务器的角度再进行一次帧率优化"
> ★ 先说结论：**服务器 tick 现在不是瓶颈**（余量 93%+）。所以服务器侧的价值不在"救 tick"，
>   而在**帮客户端省 CPU/带宽** —— 那才是"多实体战斗"真正卡的地方。

### 12.1 实测（`tools/perf_server.py`，离线跑 World，不连网络）

| 场景 | tick 耗时 | 30Hz 预算是 33ms，余量 |
|---|---|---|
| 1 玩家 · 5 怪 | 0.105 ms | 99.7% |
| 1 玩家 · 25 怪 | 0.671 ms | 98.0% |
| 1 玩家 · 45 怪 | 1.377 ms | 95.8% |
| 1 玩家 · 60 怪 | 1.883 ms | 94.3% |
| 3 玩家 · 45 怪 | 1.565 ms | 95.3% |
| 3 玩家 · 60 怪 | **2.141 ms** | **93.5%** |

拆分（40 怪）：

| 项 | 耗时 | 说明 |
|---|---|---|
| 快照构造 + JSON 序列化（单玩家） | **0.071 ms** | 很小 |
| 同上（3 玩家，每人各做一遍） | **0.209 ms** | 重复劳动，但绝对值也小 |
| 怪 AI（`_mob_tick`） | 占 tick 的 **87%**（cProfile：1.17 / 1.345 ms） | 热点是它 |
| `mob.wire()` 被调 36000 次/300 tick | 0.065 ms 累计 | 每只怪每帧都给每个玩家序列化一次 |

★ 换成大白话：
　**40 只怪 3 个人一起打，服务器每帧只花 2 毫秒，还有 31 毫秒闲着。**
　所以"服务器卡"目前不存在；但如果玩家/怪继续涨（100 怪 × 10 人），会先卡在
　① 每帧 `玩家数 × 怪数` 的视野过滤 ② `mob.wire()` 重复构造 ③ 每玩家重复序列化。

### 12.2 服务器侧优化清单（按"对客户端帧数有没有帮助"排序）

| # | 做什么 | 帮谁 | 体验影响 | 工作量 |
|---|---|---|---|---|
| S1 | **公共部分只序列化一次**：mob 数组拼成字符串缓存，每个玩家只拼自己的头（现在每人重跑一遍 `json.dumps`） | 服务端 CPU（多玩家时线性省） | **无** | 小 |
| S2 | **增量快照**：只发"这一帧有变化的怪"（位置变了/血量变了/新出现/消失），客户端按 id 合并 | **客户端 JSON 解析 -40~60%、带宽 -50%** | **无**（客户端本来就是插值） | 中 |
| S3 | **坐标量化**：`x/z` 用厘米整数、`yaw` 用 1/100 弧度；字段名已是最短 | 带宽 -15%，解析快一点 | **无**（现在精度 0.001 米本来就是浪费） | 小 |
| S4 | **空间网格**：`_mobs_for` / 怪找玩家改成按格查邻域（现在每帧遍历全部怪 × 全部玩家） | 服务端 CPU（100 怪时明显） | **无** | 中 |
| S5 | **`mob.wire()` 复用**：每只怪每帧只构造一次 dict，多个玩家共享只读 | 服务端 CPU | **无** | 小 |
| S6 | **存档分帧**：15 秒一次的全量存盘摊到每 tick 存 2 个玩家（现在会有一帧突然多做几十次串行化） | 服务端抖动 | **无** | 小 |
| S7 | 远怪 20Hz（客户端插值） | 客户端解析/带宽 | **需要你点头**（远怪位置最多晚 50ms，插值后基本看不出） | 中 |

★ S1~S6 是**纯实现优化**：数值、判定、时序、客户端看到的画面都不变。
★ S7/S8 严格说是"行为时序的微调"，所以单独拎出来问你要不要。

### 12.3 顺手能做的"服务器帮客户端减负"

- 怪的数量上限（`MOB_RENDER_CAP`）现在是**按视野**发的；可以再按"屏幕方向"过滤（背对玩家的怪不发）——**无感**，包再小 20%
- 掉落在远处的（>30m）不发给这个玩家 —— 现在可能发了但他根本看不到
- 别人的挥砍序号（`atk`）只在变化时发（现在是每帧带）

## 13. 这些优化会不会改变玩法和体验？（逐条对照）

### 13.1 玩法层面：**零改动**

| 类别 | 结论 |
|---|---|

### 13.2 视觉/体验层面：分三类

**A. 完全无感（纯实现优化）—— 可放心做**

### 17.2 拖影怎么做的

- 把刀尖最近 **12 帧**的世界坐标连成一条三角带（`TRAIL_N = 12`）
- 器材：`MeshBasicMaterial` + **加法混合** + `depthWrite:false`（不会挡住后画的东西）
- 淡出：**新的一头亮、旧的一头压暗**（加法混合下压暗 = 淡出，不用每帧重建材质 ✓）
- 宽度 0.045 × 武器长度系数（斧 1.3 / 剑 1.15 / 匕首 0.62 / 长枪 1.6 / 弓 1.0）
- 生命周期：挥砍期间常亮（`atkT >= 0` 时 life 一直刷新）→ 收招后 0.22 秒淡出
- 成本：**1 次绘制 + 每帧 12 个点**（可忽略）

### 17.3 关键取舍

| 决定 | 原因 |
|---|---|
| 只在**自己**身上做 | 别人的拖影要按他们各自的 atkT + 武器算，先不做（不改变现有观感） |
| 用加法混合而不是透明贴图 | 不依赖任何贴图（贴图有版权问题），而且发光感更自然 |
| 拖影**不参与任何判定** | 纯视觉；命中/伤害/冷却一行没动（测试里专门验了 atkCd 照旧） |

### 17.4g 颜色"不干净 / 一段一段"的真正原因（用户第三次反馈，这次找到根了）

| 现象 | 根因 | 修 |
|---|---|---|
| 红刀光里夹着白 | **加法混合**会把 R/G/B 三个通道一起相加 → 任一处叠加就趋近 1 = 白 | 换成**普通透明混合**（NormalBlending）|
| 颜色灰蒙蒙 | 颜色直接乘了 alpha（`col = 颜色 × a`）→ 等价于"把颜色变暗" | 颜色写**品阶本色**，透明度单独写进 **alpha 通道** |
| 一道一道的条带 | ① 同一帧补出来的中间点**时间戳相同** → 颜色按帧跳变<br>② 几何按固定点数画，多出来的退化四边形在尾巴上留亮斑 | ① 中间点时间戳**按插值算**<br>② `setDrawRange` 只画真实存在的段 |
| 不够细 | 宽度 0.072 仍偏粗 | 宽度 → 0.036 → **0.018**（用户连要两次"再细一半"）|

**实现要点**：`color` 属性改成 **4 通道**（RGBA）—— three 看到 `itemSize === 4` 会自动启用逐顶点 alpha
（`USE_COLOR_ALPHA`），这样"颜色纯 + 透明度独立"两件事才能同时成立。

对照图：`docs/shots/trail_t7.png`（7 阶，纯品红、细线状）· `docs/shots/trail_t10.png`（10 阶，淡金）

## 20. 修正：暴击定格为什么"没感觉"（2026-10-18）

|---|---|---|

40 只怪 × 4 条肢体 = **每帧 160 次 rotation 写入**，然后 three 还要为这 160 个 Group 算矩阵。
但其中很大一部分是白算的：

| 情况 | 现状 | 该不该算 |
|---|---|---|
| > 18 米（已切静态 LOD，四肢根本不画） | 照算 | **不该** ✗ |
| 屏幕外（投影落在视口外） | 照算 | **不该** ✗ |
| 8~18 米（摆臂相位差 33ms 看不出） | 照算 | 隔帧算就够 ✓ |
| < 8 米 | 照算 | 该算 ✓ |

### 24.2 改法

在妖兽循环里加一个 `_poseSkip` 判定（**只跳"摆姿"，位置插值/血条/名牌一律照常**）：

```js
var _poseSkip = (距离 > 18米) || (屏幕外) || (距离 > 8米 && 隔帧 && 没在攻击);
```

屏幕外怎么判的：算名牌投影那一步本来就算了一次投影 ✓ 顺手记 `rm._offscreen` ✓ 零额外开销。

## 25. 执行记录：A1 四肢实例化（2026-10-18，本轮最大的一笔）

### 25.1 先量清楚 314 次绘制花在哪

| 项 | 数值 | 结论 |
|---|---|---|
| 40 只怪同屏，主渲染绘制调用 | **314** | — |
| 关掉阴影之后 | 314（不变） | **阴影不计入这个数** |
| 隐藏所有四肢之后 | **154** | **四肢正好占 160 次**（40×4）|

→ 所以四肢实例化是唯一能"砍一半绘制"又不改画面的事。

### 25.2 怎么做的（动画代码一行没改）

| 步骤 | 做法 |
|---|---|
| ① 枢轴只当"姿势容器" | `mob()` 里照旧建 legL/legR/armL/armR 四个 Group，但**不再挂到模型上**（不参与渲染），只用来存 `rotation` |
| ② 按肢体类型分桶 | `(手臂/腿 × 粗细 × 颜色)` 各建一个 `InstancedMesh`（容量 256）|
| ③ 每帧写实例矩阵 | `模型世界矩阵 × 平移(枢轴) × 旋转(姿势)` → 和原来挂在模型上**完全等价** |
| ④ 倒地/淡出/LOD | 把这 4 个 Group **挂回模型**（这样它们跟身体一起转、一起淡）✓ 实例槽清零 |
| ⑤ 受击闪白 | 给这一只的实例颜色乘亮（`instanceColor`）→ 肢体也会闪 ✓ |

**为什么不改动画代码**：攻击/走路/倒地那些逻辑写的都是 `hh.legL.rotation.x = ...`，
现在这些 Group 仍然存在、仍然被写 → 只是渲染时读的是它们的值，而不是它们的顶点 ✓

### 25.3 实测

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 绘制调用（40 只怪） | **314** | **169（-46%）** |
| 三角形 | 32.4k | **32.3k（没变）** |
| 肢体批次数 | 160 个独立网格 | **16 个实例化批** |

★ 关键：三角形没变 → 画的东西一模一样，只是提交方式变了 ✓

### 25.4 两个必须记住的坑

1. **`InstancedMesh` 的 `count` 默认 = 容量（256）** ✗
   不改成"实际用到几个"，就会把 256 个空槽全画一遍 → 三角形从 32k 涨到 **80k** ✗
   修：创建后 `mesh.count = 0`，分配一个槽 +1 ✓
2. **删怪时必须把它的实例槽清零** ✗
   不清 → 腿会一直停在它死的地方（"幽灵腿"）✗ 修：`removeWorldMob()` 里 `limbZero()` ✓

## 32. 进游戏加载提速（2026-10-18）

> 用户："优化一下进游戏的加载速度，有没有比较好的方案"
> 用户追问："缓存的话有更新时这样不会跑到旧程序吧"

### 32.1 先量（改之前）

| 类别 | 体积 | 请求数 | 占比 |
|---|---|---|---|
| **音效（wav）** | **1935 KB** | 35 | **57%** ✗ |
| three.min.js | 594 KB | 1 | 没压缩 |
| core/game.js | 378 KB | 1 | 没压缩 |
| platform/web.js | 327 KB | 1 | 没压缩 |
| 贴图 | 137 KB | 9 | 4% |
| **合计** | **3371 KB** | **48** | — |

服务端原来一律发 `Cache-Control: no-store` → **每次刷新都要重下全部 3.4MB** ✗✗

### 32.2 三条改动

| # | 改动 | 效果 |
|---|---|---|
| ① | **gzip 文本资源**（js/html/css/json/svg，>1KB）| game.js 378KB → **141KB（37%）** |
| ② | **ETag + 304**：静态文件带 ETag；`?v=构建号` 对得上 → 长缓存，对不上 → no-cache | 刷新时 **0KB**（全部 304）|
| ③ | **音效 ogg 优先 + 按需加载**：启动只拉 3 组核心（约 30KB），其余进世界后后台补 | 音效 1935KB → **491KB** |

★ 为什么音效换 ogg：目录里同名的 ogg 每个才 5~14KB，wav 是 50~140KB；
　 解码都是一次性的，播放时都是内存里的 AudioBuffer → **听感一样**，体积 1/4 ✓

### 32.3 结果

| 指标 | 改之前 | 改之后 |
|---|---|---|
| 首屏（进世界那一刻） | 3371 KB / 48 请求 | **约 650 KB**（JS 480 + 音效 30 + 贴图 137）|
| 音效总量 | 1935 KB | **491 KB** |
| 刷新页面（第二次） | 3371 KB | **0 KB（304）** |
| JS 单文件 | 378 KB | **141 KB（gzip）** |

4G 上大约从 **2~3 秒** 降到 **0.5 秒以内**（还剩 RTT 和解析）。

### 32.4 「缓存会不会跑到旧程序」——不会，三层保障

| 保障 | 机制 |
|---|---|

## 37. 修：「改了代码但看着没变化」（缓存，2026-10-18）

> 用户："为什么我看没有变化，是不是缓存的问题，刚刚我做的优化"

**确实是缓存，但不是 Service Worker** —— 是 HTML 的 ETag 漏了构建号：

| 环节 | 原来的行为 |
|---|---|
| JS 地址 | `?v=<构建号>`，构建号 = 四个前端文件里最新的 mtime ✓ |
| 只改了 game.js | 构建号变了 ✓，但 **index.html 没变** ✓ |
| 浏览器问 HTML | `If-None-Match` → 服务器算出的 ETag 只看 index.html 的 mtime/大小 → **回 304** ✓ |
| 结果 | 浏览器用**缓存里的旧 HTML** → 里面写的是**旧 `?v=`** ✓ |
| 旧 `?v=` 地址 | 被标了 `immutable`（一年）→ 直接读本地缓存 ✗✗ |
| **现象** | **改了代码、刷新、看起来什么都没变** ✓✓ |

**修**：HTML 的 ETag 里带上构建号 ✓
```python
if 'text/html' in ctype:
    etag = '"%x-%x-%s"' % (mtime, size, self._web_build())
```
→ JS 一变构建号就变 → HTML 的 ETag 也变 → 浏览器必须重新下载 HTML → 新 HTML 引用新 `?v=` → 新 JS ✓

**另外**：页面里加了 `<meta name="build" content="1792312641">`，
「设置 → 关于」会显示这个号 —— 以后一眼就能确认"我到底跑的是不是新版本" ✓

### 38.5 追问修复：断线后"重连了但进不去，只能重启 APP"（round464）

用户补充："掉线了，我自己点重连加载不进去了，只能关了 APP 重新进才行"

#### 真因：**断线后会自动整页刷新**

代码里有两处"掉线 → `location.reload()`"：

| 位置 | 什么时候触发 |
|---|---|
| `ws.onclose` | 每次连接断开（第 186 轮加的"断开自动刷新一次"）|
| 不同步看门狗 | 8 秒没收到世界数据 → 又刷一次 ✗ **几乎每次都触发** |

在浏览器的标签页里刷新没问题 ✗ **但在 APK 的 WebView 里**：
- 刷新要经过 **Service Worker**（network-first，离线时回退旧缓存）
- 还要重新走一遍**加载遮罩**（#boot）
- 这一步一卡 → 一直停在"正在载入资源…" → 玩家看到的正是"加载不进去" ✓✓
- 而"关掉 APP 再开" = 全新的 WebView 进程 → 没有这些残留状态 → 能进 ✓

#### 修法

| # | 改动 |
|---|---|
| A | **断线不再刷新页面** ✗ 改成 `netHardReconnect()`：摘掉旧 socket 的回调 → 关掉 → 重连 → 重新 hello ✓ |
| B | 不同步看门狗也从"刷新"改成"原地硬重连" ✓ |
| C | 加载遮罩加 **20 秒铁超时**（到点无论如何收掉，绝不允许"永远加载中"）✓ |
| D | 断线横幅加第二个按钮「刷新」（真要整页刷新时玩家自己点，带 `?fresh=时间戳` 绕开 SW 缓存）✓ |
| E | `kick` 只有 `auth` / `norole` 才清 token；`ver`（版本不符）/ `dup`（别处登录）保留 token，只提示 ✓ |

★ E 的原因：以前任何 kick 都清 token → 下次刷新直接掉回登录框 → APK 里输入不方便 → 感觉"进不去" ✓
